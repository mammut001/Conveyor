# Conveyor 路线图

这份路线图汇集 README 中的方向，并将未来目标与仓库中已有能力分开。它是规划而非发布日期或交付承诺；实现状态以代码、配置和各功能文档为准。

## 当前代码基础与待完成事项

- **多入口与现有功能**：仓库包含 Telegram、飞书和 Web 入口，以及聊天、任务、审批和桌面相关代码；各能力的实际部署和启用状态需要单独核实。
- **Supervisor 工作区代码**：已在本分支提交（尚未合并到 `main`），包括可配置的协调、分析、实现和审阅角色，以及任务状态、工作树锁、交接、验收和部署阶段的记录。Web 的「项目」页可以派发任务，派发后由后台 worker 运行分析、实现、审阅和有限修复循环。参见 [架构总览](architecture-overview.md)。
- **执行器现状**：Claude Code、Command Code、Antigravity（agy）和内置 Pi（`pi`）执行器已实现。`pool`（执行者池）按用量和额度在 Claude Code、Command Code 和 Antigravity 之间轮换。Supervisor 内的 Codex 适配器仍未实现，选用时明确报不可用。角色或模型的示例不是线上配置的证据。
- **执行者池**：「执行者」页可以检测、登录、拖动排序和设置用量阈值；额度类失败后自动换下一个执行者。Pi 与 Super Grok 不参与 `pool` 轮换。
- **目标驱动闭环（阶段 5 代码基础）**：已实现目标循环与「项目」页「目标」界面（见 [目标使用指南](goals.md) 与 [Supervisor 文档](agent-supervisor.md)）：
  - **代码强制规则的目标循环**：在同一受管工作树上按轮派发任务并由协调模型评估下一步；仅当最新一轮任务 `completed`（宿主机自动检查通过）时才允许判为 `achieved`，未配置自动检查必进 `waiting_user`，轮数上限、任务取消和缺失均由代码硬规则兜底，不信任模型自报。
  - **按仓库勾选自动检查**：服务端扫描仓库根目录识别候选检查项，用户在页面勾选，不接受浏览器提交任意命令。
  - **改动查看与对比**：支持按单轮任务或整个目标查看文件增删与逐行差异。
  - **用户确认的本地合并**：预览阻塞项并在用户显式确认后将受管工作树改动合入主工作目录默认分支，拒绝忙工作树、脏主工作目录、非默认分支及带命令执行风险的仓库配置，冲突自动撤销恢复，绝不自动推送。
  - **状态通知**：目标进入需回复或结束状态（`waiting_user` / `achieved` / `exhausted` / `failed`）时，通过 Telegram、飞书与 Web Push（仅含固定标题与目标 ID，正文不出机）发送去重中文提醒。
- **待贯通与未验证**：
  - Supervisor 功能开关（`CONVEYOR_AGENT_SUPERVISOR_ENABLED`）默认关闭。
  - 尚未记录真实模型在真实仓库与真实任务上的端到端运行结果（当前目标闭环与单任务流程的验证来自单元测试和假 CLI 烟测）；取消、进程恢复、工作区快照验收和审阅权限仍待真实运行验证。
  - 没有自动部署：部署阶段仍只是 SQLite 状态记录，合并也仅在本地完成、不会自动推送或上线；必须以实际运行证据区分开发完成、本地合并和部署成功。
  - 额度提示识别：agy 已用真实输出验证（「Individual quota reached … Resets in 139h56m47s」，有回归测试）；claude 和 cmd 的真实额度提示还没有对照过，目前靠通用关键词匹配。
  - Command Code 无界面（`-p`）运行时，2026-11-08 本机实测 `accept-edits` 与 `dont-ask` 都写不了文件，只有 `--yolo` 能写，而无人值守时不应使用 `--yolo`。因此它目前更适合只读的分析和审阅，不适合当实现角色。
  - Antigravity 的实时用量需要本机正在运行的语言服务进程。没有该进程时拿不到用量，只能等额度报错后再轮换。

## Ultimate：用户负责灵魂，Agent 负责迭代

最终理想是解放双手：用户提供灵感、目标、品味和最终判断；Agent 理解意图，自主拆解、写代码、运行验证、观察结果并持续迭代，直到成果符合目标。Conveyor 则让这一过程在用户自己的环境中持续运行，并让用户随时看得见、能介入、能叫停。

从现有基础走向这个愿景，可以分为几个互相衔接的阶段：

1. **看得见的单次执行**：可靠地接收目标，执行任务，呈现进度、验证结果和改动，支持审阅、应用或丢弃。这是已有基础，仍需持续提高可靠性。
2. **连续迭代**：让 Agent 根据测试、运行结果和用户反馈继续修改，保留上下文，并在遇到无法自行解决的问题时说明阻碍。
3. **主动发现与反馈**：持续观察项目健康、失败和待办，提出有依据的下一步；由用户设定目标和主动程度。
4. **协同与长期运行**：探索多个 Agent 在不同工作区中分工、协调和恢复，积累项目记忆，并保持清晰的任务归属与审阅记录。
5. **目标驱动的闭环**：用户描述想达到的结果，Agent 自主规划、实现、验证和迭代，在需要用户判断或授权时及时交还控制。目前仓库已实现这一阶段的核心本地闭环（见 [目标使用指南](goals.md)）：包含由代码强制规则兜底的目标循环、按仓库勾选自动检查、全目标改动对比、经用户确认的本地主分支合并，以及需回复或结束时的通知提醒；但 Supervisor 功能开关（`CONVEYOR_AGENT_SUPERVISOR_ENABLED`）默认关闭，尚未记录真实模型的端到端运行结果，也没有自动部署。

以上各阶段仍是规划而非交付承诺；代码具备局部能力不等于已在真实模型和生产环境中完整验证，顺序与范围会随实际验证调整。自动化程度越高，越需要可靠的验证、可观测性、停止机制和明确的权限边界。
