# Conveyor 路线图

这份路线图汇集 README 中的方向，并将未来目标与仓库中已有能力分开。它是规划而非发布日期或交付承诺；实现状态以代码、配置和各功能文档为准。

## 当前代码基础与待完成事项

- **多入口与现有功能**：仓库包含 Telegram、飞书和 Web 入口，以及聊天、任务、审批和桌面相关代码；各能力的实际部署和启用状态需要单独核实。
- **Supervisor 工作区代码**：已在本分支提交（尚未合并到 `main`），包括可配置的协调、分析、实现和审阅角色，以及任务状态、工作树锁、交接、验收和部署阶段的记录。Web 的「项目」页可以派发任务，派发后由后台 worker 运行分析、实现、审阅和有限修复循环。参见 [架构总览](architecture-overview.md)。
- **执行器现状**：Claude Code、Command Code 和 Antigravity（agy）执行器已实现。`pool`（执行者池）按用量和额度在这些执行者之间轮换。Supervisor 内的 Codex 适配器仍未实现，选用时明确报不可用。角色或模型的示例不是线上配置的证据。
- **执行者池**：「执行者」页可以检测、登录、拖动排序和设置用量阈值；额度类失败后自动换下一个执行者。Pi 与 Super Grok 不参与 Supervisor 执行。
- **待贯通与未验证**：
  - 真实 CLI 的额度提示文本尚未与 claude、agy、cmd 的真实输出对照，目前使用通用关键词匹配。
  - Command Code 无界面（`-p`）运行时，2026-11-08 本机实测 `accept-edits` 与 `dont-ask` 都写不了文件，只有 `--yolo` 能写，而无人值守时不应使用 `--yolo`。因此它目前更适合只读的分析和审阅，不适合当实现角色。
  - Antigravity 的实时用量需要本机正在运行的语言服务进程。没有该进程时拿不到用量，只能等额度报错后再轮换。
  - 在真实仓库和真实任务上跑通端到端流程，并验证取消、进程恢复、工作区快照验收和审阅权限；以实际运行证据区分开发完成、合并和部署成功。

## 后续方向

- [ ] 将分析、实现、独立审阅和修复循环做成可观察、可恢复的真实端到端流程。
- [ ] 支持适合实际工作方式的执行器，明确不可用原因，不静默替换。
- [ ] 完善多工作区调度、锁与并发隔离，并对代码版本和未提交改动建立可靠验收依据。

- [ ] 探索语音输入与任务交互。

## Ultimate：用户负责灵魂，Agent 负责迭代

最终理想是解放双手：用户提供灵感、目标、品味和最终判断；Agent 理解意图，自主拆解、写代码、运行验证、观察结果并持续迭代，直到成果符合目标。Conveyor 则让这一过程在用户自己的环境中持续运行，并让用户随时看得见、能介入、能叫停。

从现有基础走向这个愿景，可以分为几个互相衔接的阶段：

1. **看得见的单次执行**：可靠地接收目标，执行任务，呈现进度、验证结果和改动，支持审阅、应用或丢弃。这是已有基础，仍需持续提高可靠性。
2. **连续迭代**：让 Agent 根据测试、运行结果和用户反馈继续修改，保留上下文，并在遇到无法自行解决的问题时说明阻碍。
3. **主动发现与反馈**：持续观察项目健康、失败和待办，提出有依据的下一步；由用户设定目标和主动程度。
4. **协同与长期运行**：探索多个 Agent 在不同工作区中分工、协调和恢复，积累项目记忆，并保持清晰的任务归属与审阅记录。
5. **目标驱动的闭环**：用户描述想达到的结果，Agent 自主规划、实现、验证和迭代，在需要用户判断或授权时及时交还控制。

后面各阶段是愿景和规划，并非已经交付的能力；顺序与范围会随实际验证调整。自动化程度越高，越需要可靠的验证、可观测性、停止机制和明确的权限边界。
