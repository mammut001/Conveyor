# General Routines (P1-4)

General Routines allow Conveyor to execute scheduled natural-language tasks via the chat tier and tools, delivering results to a Web Console inbox and optionally to Telegram or Feishu.

## Overview

Unlike legacy fixed-purpose scheduled tasks (e.g. reminders, daily briefings), a General Routine runs an arbitrary natural-language prompt on a schedule.

Each run goes through Conveyor's unified chat tier (`handlers.chat.ask_chat`). If the prompt triggers read-only tools, they execute automatically; if it triggers dangerous or write actions, a pending approval is created and held for operator confirmation in the Web Console inbox.

## Configuration & Feature Flag

Routines are disabled by default. Enable them in `.env`:

```dotenv
# Enable General Routines (default: false)
CONVEYOR_ROUTINES_ENABLED=true

# Optional default Feishu delivery chat ID for routine runs
# CONVEYOR_ROUTINES_FEISHU_CHAT_ID=oc_xxx
```

When disabled, all routine API endpoints return HTTP 409 (`{"error": "routines are disabled (set CONVEYOR_ROUTINES_ENABLED=true)"}`) and `routine.*` tools are hidden from the chat model.

## Key Design Constraint: Where the Runner Executes

**The routine runner runs inside the Web Console process (`web_console.py` / `web_console_takeover.py` `main()`, via `routines.start_routines_worker`), NOT in the oneshot `scheduler_tick.py` process.**

### Rationale
Pending tool confirmations in Conveyor live **in-memory** in the process that created them (`handlers/tools/confirm.py`). The Web Console decides approvals via `/api/approvals`. If routines were executed in a separate short-lived cron process like `scheduler_tick.py`, any approvals generated by write tools would be stored in the memory space of that dying process and could never be decided by the Web Console.

By executing on the asyncio event loop of `web_console.py`:
- Any write tools called by a routine generate a pending confirmation token directly in the Web Console process.
- The approval appears in the Web Console inbox and `/api/approvals`.
- The operator can approve or deny the action directly from the web interface.
- Routines themselves are persisted in SQLite (`<codex_memory_root>/routines.db`) so that other processes (such as Telegram or Feishu bots) can create, list, pause, or resume routines via chat tools.

## Cron Syntax & Timezone

Routines use standard 5-field cron syntax:

```text
┌───────────── minute (0 - 59)
│ ┌───────────── hour (0 - 23)
│ │ ┌───────────── day of the month (1 - 31)
│ │ │ ┌───────────── month (1 - 12)
│ │ │ │ ┌───────────── day of the week (0 - 6) (0 to 6 are Sunday to Saturday; 7 is Sunday)
│ │ │ │ │
* * * * *
```

Supported expressions:
- `*`: all values in the field's range
- Numbers: `5`, `12`
- Ranges: `1-5`, `9-17`
- Lists: `1,15`, `0,12`
- Steps: `*/5`, `a-b/n`

### Day-of-Month and Day-of-Week OR Semantics
In accordance with standard POSIX cron semantics, when **both** day-of-month and day-of-week are restricted (neither is `*`), a day matches if **either** the day-of-month matches **or** the day-of-week matches. If only one field is restricted, only that field is evaluated.

### Timezone & Daylight Saving Time
Next fire times are evaluated in `settings.user_timezone` (`USER_TIMEZONE` in `.env`, default `America/Toronto`) using Python standard library `zoneinfo.ZoneInfo`, and stored as aware UTC timestamps. Clocks jumping forward (spring forward) or backward (fall back) are handled safely without skipping or repeating unintended wall-clock times.

## Execution & Delivery

On each execution:
1. The routine prompt is prefixed with a context note: `[Scheduled routine '<name>' running at <local time>; the operator is not watching live]`.
2. Short-term chat memory for the routine key (`web:routine-<id>`) is reset so previous runs do not pollute current output.
3. The prompt is passed to `handlers.chat.ask_chat` with a collecting `RoutinePort`.
4. Outputs are redacted for secret material and truncated to 4,000 characters.
5. Delivery:
   - **Web Inbox**: Always delivered and stored in the `routine_runs` table in SQLite.
   - **Telegram**: When `"telegram"` is in the routine's `deliver` list and `TELEGRAM_BOT_TOKEN` is configured.
   - **Feishu**: When `"feishu"` is in the routine's `deliver` list and `LARK_APP_ID`/`LARK_APP_SECRET` are configured.
   - If an action requires confirmation (`approval_pending`), Telegram and Feishu notifications notify the operator that approval is required in the Web Console inbox.

## Limits & Protection

- **Maximum Routines**: 50 per instance.
- **Run History**: The 20 most recent runs per routine are retained. Older runs are automatically pruned.
- **Auto-pause**: If a routine encounters 3 consecutive failed runs (status `error`), it is automatically paused to prevent cascading failures.
- **Timeout**: Each routine execution has a 120-second timeout.
- **Catch-up Prevention**: On server startup, routines missing `next_run_at` are scheduled for their next fire time. Missed runs older than 10 minutes are not executed in bulk.

## Web API

All endpoints are authenticated with the Web Console bearer token.

- `GET /api/routines` — List all routines with status, schedule, next run, and last run status.
- `POST /api/routines` — Create a routine (`{name, schedule, prompt, deliver?: ["web", ...], enabled?: true}`). Returns HTTP 201.
- `POST /api/routines/<id>/pause` — Pause a routine.
- `POST /api/routines/<id>/resume` — Resume a routine (recomputes next run time).
- `POST /api/routines/<id>/run` — Trigger an immediate execution. Returns run record.
- `DELETE /api/routines/<id>` — Delete a routine and its run history.
- `GET /api/inbox?limit=50` — List inbox runs (newest first) with approval statuses and unread count.
- `POST /api/inbox/<run_id>/read` — Mark an inbox item as read.
- `POST /api/inbox/read-all` — Mark all inbox items as read.
- `POST /api/approvals/<id>/approve|reject` — Existing approval endpoints also resolve routine tool approvals and update the run's recorded outcome.

## Chat Tools

Routines can also be managed through conversation in Telegram, Feishu, or Web Chat:

- `routine.list` (READ): List all configured routines.
- `routine.create` (WRITE, requires confirmation): Create a routine using the format `<5-field cron> | <prompt> [| <name>]`.
- `routine.pause` (WRITE_SAFE): Pause a routine by ID.
- `routine.resume` (WRITE_SAFE): Resume a routine by ID.
- `routine.delete` (WRITE): Delete a routine by ID.
- `routine.run` (WRITE): Queue a routine to run on the Web Console worker's next tick (within ~30s). The chat tool never executes the routine inline, because routine approvals must live in the Web Console process.

## Limitations

- Pending approvals are in-memory; restarting the Web Console drops undecided routine approvals (the inbox entry stays `approval_pending`).
- Personal data created by routines is owned by the `web-console` operator.
